# 04 · 技术架构设计

## 一、总体架构

```
┌──────────────────────────────────────────────────────────────┐
│                         客户端层                              │
│  app/ 鸿蒙 ArkTS App（HarmonyOS NEXT, ArkUI, API 24）         │
│  Account Kit（登录）   Health Service Kit（健康数据）          │
└───────────────────────────┬──────────────────────────────────┘
                            │ HTTPS / JSON
                            ▼
┌──────────────────────────────────────────────────────────────┐
│  api/ 统一后端（单个 Spring Boot，基于 RuoYi-Vue-Plus 改造）      │
│  ├─ 管理端接口：若依内置 /login /system/** /monitor/**         │
│  ├─ App 端接口：/app/v1/**（shanheng-app 业务模块）            │
│  ├─ 认证双轨：管理端若依 Token；App 端自定义 JWT               │
│  └─ 端口 8080                                                │
└───────────────┬──────────────────────────┬───────────────────┘
                │                          │
                ▼                          ▼
  maneger-web/ 若依管理前端       MySQL 8.0 + Redis 7
  （Nginx 托管，/prod-api 反代）    （Docker Compose）
                                          │
                                          ▼
                                 Cloudflare R2（菜品图片）
```

**核心变化**：不再拆成两个 Spring Boot。`api/` 一个后端同时承载「管理端接口」和「App 端接口」，`maneger-web/` 只保留若依 Vue 管理前端。

---

## 二、为什么合并成一个 Spring Boot（关键决策）

用户原方案中"api 业务后端 + RuoYi 管理后端"是两个 Spring Boot。实际上 RuoYi 本身也是 Spring Boot，**完全可以合并**：

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 两个后端 | 业务与运营物理隔离 | 两套部署/端口、两个后端写同一批表有数据归属风险、运维成本翻倍 |
| **一个后端（推荐）** | 一套部署、一个端口、无跨服务双写、开发量小 | 管理端与 App 端同进程（通过安全链隔离） |

**结论**：本项目采用**单后端**。`api/` = 若依后端模块 + 膳衡 App 业务模块，`maneger-web/` = 若依 Vue 前端。

## 三、前端架构（app/）

### 3.1 技术栈

| 项 | 选择 |
| --- | --- |
| 语言 | ArkTS |
| UI | ArkUI 声明式 |
| 最低/目标 API | compatibleSdkVersion 6.1.1(24) |
| 网络 | `@ohos.net.http` 封装 |
| 状态管理 | `@State` / `@Observed` / `AppStorage`（MVP 不引入重型框架） |
| 路由 | `router` / `Navigation` |
| 图片 | 远程 R2 URL + 本地缓存 |
| 华为服务 | Account Kit SDK、Health Service Kit SDK |

### 3.2 目录规划

```
app/entry/src/main/ets/
├── entryability/         # 入口 Ability
├── pages/                # 页面：Index/Login/Discover/DishDetail/Recommend/HealthAuth/Profile
├── common/               # 常量、工具、网络封装
├── model/                # 数据模型（DTO）
├── services/             # API 调用封装、HealthKitService
├── components/           # 通用组件
└── viewmodel/            # 页面状态
```

### 3.3 关键设计

- **网络层**：统一封装，自动携带 App 端 JWT，401 自动跳登录。
- **游客态**：本地生成设备 UUID 作为游客标识。
- **健康数据**：Health Kit 读取逻辑封装在 `services/HealthKitService`，只输出摘要。
- **图片**：R2 公网 URL 加载，列表用缩略图。

## 四、后端架构（api/）

### 4.1 技术栈（对齐若依）

| 项 | 选择 | 说明 |
| --- | --- | --- |
| 语言/框架 | Java 17 + Spring Boot 3.x | RuoYi-Vue-Plus（dromara）主线，开箱即用 |
| ORM | MyBatis-Plus | RuoYi-Vue-Plus 自带，App 业务模块直接复用 |
| 安全 | sa-token（管理端）+ JWT（App 端） | 双端路径隔离 + 账号体系分离 |
| 缓存 | Redis 7 | 验证码、管理端 token、热点数据 |
| 数据库 | MySQL 8.0 | 见 4.5 |
| 对象存储 | Cloudflare R2 | S3 兼容 SDK |
| 构建 | Maven | |

> 说明：RuoYi-Vue-Plus 为 dromara 社区增强版，主线已支持 JDK 17 + Spring Boot 3.x + MyBatis-Plus + sa-token + Vue3 前端；开工前务必以官方稳定分支的版本要求为准。

### 4.2 工程结构（api/ 内）

```
api/
├── pom.xml                  # RuoYi-Vue-Plus 父 POM
├── ruoyi-admin/             # 启动模块（依赖 shanheng-app）
├── ruoyi-framework/         # 框架：sa-token、配置、Redis、MyBatis-Plus
├── ruoyi-system/            # 系统模块：sys_* 表
├── ruoyi-common/            # 通用工具
├── ruoyi-generator/         # 代码生成器
└── shanheng-app/            # 新增：膳衡 App 业务模块
    ├── controller/          # /app/v1/**
    ├── service/
    ├── mapper/
    ├── entity/              # sh_* 表实体
    ├── dto/                 # 请求/响应对象
    └── security/            # App JWT 过滤器

> 模块名以 RuoYi-Vue-Plus 实际仓库结构为准（不同版本可能有调整）。
```

### 4.3 认证双轨设计

| 端 | 路径 | 认证方式 | 账号体系 |
| --- | --- | --- | --- |
| 管理端 | `/login`、`/system/**`、`/monitor/**`、`/tool/**` | sa-token（Plus 默认） | `sys_user` |
| App 端 | `/app/v1/**` | JWT（Authorization: Bearer） | `sh_user` |

**实现要点**：

- RuoYi-Vue-Plus 默认以 sa-token 做管理端认证；App 端可复用 sa-token 的 JWT 插件（设置独立 token 风格与登录类型）或自写 JWT 过滤器，按 `/app/v1/**` 路径放行。
- 两套账号体系隔离：后台运营账号用 `sys_user`，App 用户用 `sh_user`，互不干扰。
- 实现细节以 RuoYi-Vue-Plus 官方集成文档为准。

### 4.4 数据职责（单后端内模块约定）

单后端后不再有跨服务双写，但**代码层仍按模块约定**：

| 表 | App 模块（shanheng-app） | 管理端（若依 system + 代码生成器） |
| --- | --- | --- |
| `sys_*` | ❌ 不碰 | ✅ 读写 |
| `sh_category/sh_tag/sh_dish/sh_recommendation_rule` | 只读（提供菜单/推荐） | ✅ 读写（运营维护） |
| `sh_user/sh_health_summary/sh_recommendation_record/sh_favorite/sh_browse_history` | ✅ 读写 | 只读（查看/统计） |

### 4.5 数据库选型：MySQL 8.0（结论）

**选 MySQL 8.0，不选 PostgreSQL。理由：**

| 维度 | MySQL 8.0 ✅ | PostgreSQL ❌（本项目） |
| --- | --- | --- |
| 若依兼容性 | 原生支持、默认驱动、案例最多 | 需适配，社区 PG 版非主线 |
| 国内生态 | 企业主流、云厂商支持好 | 生态较少 |
| Java 集成 | MyBatis/MyBatis-Plus 契合 | 也支持，但若依对 MySQL 优化成熟 |
| 功能匹配 | 本项目以关系表为主，JSON 需求轻 | JSONB/全文检索优势本项目用不到 |
| 风险 | 低 | 若依改造额外成本 |

**结论**：MySQL 8.0.x，字符集 `utf8mb4`，引擎 InnoDB。

### 4.6 对象存储：Cloudflare R2

| 项 | 说明 |
| --- | --- |
| 选型理由 | 免费 10GB 存储、**无流量费**，S3 兼容 API |
| 用途 | 菜品图片、App 静态运营图 |
| 上传方式 | 管理端上传 → 后端生成预签名 URL → 前端直传 R2（或后端中转） |
| 访问 | 公网读 URL + 可选自定义域名 / CDN |
| 注意 | 菜品图压缩为 WebP，单图 ≤ 2MB |

